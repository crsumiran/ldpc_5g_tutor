CHECKPOINT 01 / 14 · 60 MINUTES

Numbers are values; bit patterns are encodings

Translate finite binary fractions into exact rational values.

Paper connection: Prerequisite to §3: input representation

A computer does not store a real-number line. It stores a finite collection of bit patterns and a rule for interpreting them. Before discussing FP8, separate the mathematical value 1.5 from its encoding. The same value can have an integer-ratio description, a binary fraction, a binary64 encoding and an FP8 encoding. Equality of values does not mean equality of bytes.

In base ten, 12.5 means 1×10 + 2×1 + 5×(1/10). In base two, 1.101 means 1 + 1/2 + 0/4 + 1/8 = 1.625. Moving the binary point one place multiplies or divides by two. Consequently 110.1₂ = 1.101₂×2² = 6.5. A finite binary fraction is a rational number whose reduced denominator is a power of two. The decimal number 0.1 is 1/10, so it has no finite binary expansion.

That observation explains a common Python surprise: the float created from 0.1 is a nearby binary fraction, not the exact rational 1/10. For a numerical experiment, distinguish the exact intended decimal input from the actual binary64 input handed to the algorithm. Our oracle must answer what the algorithm should do with the actual input bits. Otherwise we can blame an algorithm for an error already introduced during input conversion.

Work through 6.5 by writing 13/2, then 110.1₂, then 1.101₂×2². All three are exactly equal. Now compare 1/10 with the exact integer ratio returned by a Python float's as_integer_ratio method. The ratio describes the stored value without decimal display rounding. You are building the habit of looking beneath formatted output.

For your first implementation, use integer numerator/denominator pairs and fractions.Fraction. These tools belong to the external test oracle. Later, putting arbitrary-precision fractions inside the emulated FP8 kernel would evade the precision contract. A tool can be appropriate for checking an algorithm while being inappropriate for implementing the algorithm itself.

CHECKPOINT 02 / 14 · 75 MINUTES

Read a binary64 value like a hardware word

Decode binary64 into sign, exponent, fraction and class.

Paper connection: §3 Type1 and §4.2 integer emulation

Binary64 uses one sign bit, eleven exponent bits and fifty-two stored fraction bits. For a normal value the significand has an implicit leading 1, so its precision is 53 bits. Precision counts meaningful binary digits; range describes the exponents you can represent. Those are different resources. A format can offer a wide range but very few useful digits at each magnitude.

For exponent field E between 1 and 2046, fraction field F and sign s, the value is (−1)^s × (1 + F/2^52) × 2^(E−1023). The stored exponent is biased: the field 1023 represents exponent zero. For 6.5 = 1.101₂×2², s=0, E=1025 and the fraction starts 101 followed by zeros. This is a bit-layout exercise, not numerical rounding.

There are exceptional categories. E=0 with F=0 encodes signed zero. E=0 with F nonzero is subnormal, with value (−1)^s F×2^−1074. E=2047 with F=0 is infinity; with F nonzero it is NaN. NaN is a category of bit patterns, not a number equal to itself. Signed zeros compare numerically equal but have different sign bits.

The spacing between normal numbers in [2^e,2^(e+1)) is 2^(e−52). Near one, the next larger value is 1+2^−52. Near two, the upward spacing doubles. This uneven grid is why a constant absolute tolerance does not describe precision equally well across magnitudes.

Use struct to reinterpret bytes rather than converting a float to int: int(6.5) gives 6, not its IEEE bit pattern. Your decoder should return fields and a classification. Only build an exact rational value for finite cases. The later integer emulator will reuse these fields, replacing floating-point arithmetic with significand shifts and integer operations. Understanding this page makes the paper's phrase “FP64 emulation” concrete.

Rounding is a rule you can implement

Implement an exact RNE decision for an integer with discarded low bits.

Paper connection: §3 rounding notation; §4.2 RNE

Suppose a hypothetical binary format retains only three significant bits. Between one and two its values are 1, 1.25, 1.5 and 1.75. An exact value between neighbors must be assigned to one of them. Round-to-nearest chooses the closer neighbor. At an exact midpoint, ties-to-even chooses the candidate whose retained integer significand ends in a zero bit. “Even” describes that integer, not whether the displayed real value is an even whole number.

The value 1.125 is halfway between 1 and 1.25. Their retained significands are 100₂ and 101₂, so the result is 1. The value 1.375 is halfway between 1.25 and 1.5; the latter significand, 110₂, is even, so the result is 1.5. Neither always rounding up nor always rounding toward zero implements this rule.

In an integer implementation, partition a significand into retained bits and discarded bits. The first discarded bit is the guard bit. A following bit is the round bit. The sticky bit is the OR of all remaining discarded bits. Guard zero means less than halfway. Guard one with any further discarded one means more than halfway. Guard one with all remaining bits zero is the tie case, where the retained low bit decides.

Rounding can create a carry: a retained 1.111… may become 10.000…. Normalization must then increase the exponent. Negative values need the same nearest-distance logic on magnitude, followed by sign restoration; shifting a negative Python integer arithmetically and calling it truncation is easy to get wrong.

For this checkpoint, start with a nonnegative integer divided by a power of two and round it to an integer. The problem is small enough to test exhaustively. Later the same decision sits inside FP8 encoding and integer binary64 multiplication. Keep this primitive separate so one corrected tie rule fixes both uses.

CHECKPOINT 04 / 14 · 120 MINUTES

FP8 E4M3: enumerate the whole number system

Implement an explicit E4M3 decoder and a documented saturating encoder.

Paper connection: §4.1 format choice; FP8 format paper and CUDA conversion API

FP8 means eight total bits. In the E4M3 encoding used for this course, one is a sign bit, four are exponent bits and three are stored fraction bits. Normal values have four significant bits including the implicit one. The exponent bias is 7. For ordinary normal exponent fields E, the value is (−1)^s × (1+F/8)×2^(E−7).

Do not blindly copy binary64 special cases. The finite-extended E4M3 convention has finite values at exponent field 15 when the fraction is 0 through 6. Its largest finite magnitude is (1+6/8)×2^8 = 448. Fraction 7 at exponent 15 encodes NaN. There is no infinity encoding. Exponent zero uses subnormal values F×2^−9, making the smallest positive subnormal 2^−9 and the smallest positive normal 2^−6. This is the NVIDIA-style E4M3 convention; formats with similar names and different zero/bias rules must not be substituted.

An encoding tells us what a byte means. A conversion policy tells us what to do with a value outside that set. In this course, the standalone encoder accepts exact finite rational inputs and uses RNE plus finite saturation: magnitudes above the finite range clamp to 448. The paper-method path must reject unintended saturation instead of hiding information loss. Infinity input maps to signed maximum finite only in the explicitly saturating adapter; NaN gets a canonical NaN byte. Test these separately from the finite rational encoder.

Decode 0x38: sign zero, exponent seven, fraction zero, giving one. Decode 0x3c: exponent seven, fraction four, giving 1.5. Decode 0x01: exponent zero and fraction one, giving 1/512. There are only 256 byte patterns, so exhaustive decoding and finite round-trip checks are practical.

E5M2 spends one more bit on exponent and one less on fraction. It buys range by losing local resolution. We teach it only as a comparison: the required kernel uses E4M3. A frequent mistake is assuming E4M3 can represent every integer through 448. It cannot: near 256, adjacent values are 32 apart.

A dot product reveals where information disappears

Separate input quantization error from accumulation error.

Paper connection: §3 inner-product formulation; §4.1 FP32 accumulation

A dot product takes two equal-length vectors, multiplies matching entries and adds the products. If x=[2,3] and y=[4,5], the answer is 2×4+3×5=23. Matrix multiplication consists of many dot products: each output combines one row of A with one column of B. This is the scientific workload we will eventually reconstruct.

There are three distinct precision decisions: how inputs are encoded, how products are formed, and how products are accumulated. A wider accumulator can prevent further loss during summation, but cannot restore bits discarded when the original inputs were converted. This is the first reason “FP8 inputs with FP32 accumulation” alone cannot deliver arbitrary FP64 accuracy.

Take x=[1.0625,−0.9375] and y=[1,1]. The exact dot is 0.125. Direct E4M3 conversion rounds 1.0625 to 1 while −0.9375 is exactly representable. Their encoded-input dot is 0.0625. An exact accumulator would still produce the wrong answer for the original inputs: the damage occurred earlier.

Now isolate accumulation. Binary32 has 24 significant bits. Every integer up to 2^24 is representable, but not every larger integer. Starting at 2^24 and adding one with binary32 RNE returns 2^24. Repeating this rounded addition does not eventually accumulate the lost ones. This experiment distinguishes an exact real sum from a repeated rounded reduction.

Your first kernel is deliberately naive so we have a meaningful comparison later. Decode E4M3 values exactly, compute their products under the specified model, and round each accumulation to binary32. Do not rely on numpy.dot's default dtype or a hidden BLAS reduction tree. On the finite E4M3 range, the products fit binary32 exactly, but arbitrary long sums may not. Preserve a trace of every rounded partial sum on small inputs.

Scaling changes range; residuals preserve information

Implement exponent selection and inspect a residual expansion without claiming it is the full Ozaki splitter.

Paper connection: §3 Eqs.4–9: preparation for slicing

Consider a camera exposure analogy only briefly: changing the scale can bring large values into a limited range, but cannot create more distinct representable levels. Numerically, multiplying by a power of two shifts the exponent while preserving significant bits as long as the result stays in range. Scaling is useful because E4M3 cannot store an arbitrary binary64 exponent.

Write a value as x = 2^c q + r. Here q is a low-precision component, c is an external integer exponent, and r is the residual. The scale lives outside the FP8 byte. If you throw away r, this is ordinary lossy quantization. If you keep r and repeat the process on it, you can build an expansion carrying more information than one byte.

For a decimal analogy, 1234 = 1200 + 34, then 34 = 30 + 4. Each term is simple; together they retain the original information. In binary arithmetic, powers of two make the rescaling especially convenient. But the actual method needs more than this analogy: components across a vector must share a grid so their dot products can accumulate exactly. Arbitrary per-element nearest-FP8 decompositions do not automatically satisfy that condition.

On a vector with maximum absolute value 6.5, choose c=ceil(log2(6.5))=3. Then dividing by eight puts all magnitudes at most one. For maximum exactly eight, c is still three. For maximum just above eight, c becomes four. The boundary case is important enough to avoid approximate decimal reasoning. For the all-zero vector, stop immediately instead of evaluating log2(0).

The invariant you should care about is reconstruction: original vector equals the sum of saved scaled components plus the current residual. Use an exact rational oracle to check it. A small norm of the residual is useful information, but is not permission to discard it when the contract is a complete decomposition.

CHECKPOINT 07 / 14 · 150 MINUTES

Use rounding deliberately to extract a slice

Implement and validate one supported Ozaki extraction step.

Paper connection: §3 Eqs.1–8

Previously rounding destroyed information. Here we deliberately use it to isolate a coarse part, then retain what was removed. The trick is to add a large offset sigma, forcing a small residual onto sigma's representable grid, and subtract sigma again. The expression must contain two separately rounded operations. Algebraic simplification would destroy the algorithm.

Let k be dot-product length. Set p1=53 for binary64, p2=4 for E4M3 and p3=24 for binary32. Define gamma=ceil(53−(24−log2(k))/2), xi=49 and rho=max(gamma,xi). There are two constraints: components must fit E4M3, and enough accumulator precision must remain for the sum of k products. Taking the larger budget enforces the more restrictive constraint.

Choose c from the current vector maximum and sigma=0.75×2^(rho+c). For each residual element r, compute t=R64(r+sigma), v=R64(t−sigma), and next=R64(r−v). Store q=E4M3(2^(−c)v). Every conversion is visible. Under the intended conditions the final E4M3 conversion is exact; otherwise our implementation must reject the split rather than silently lose bits.

For k=2, rho=49. Take x=[1.0625,−0.9375], giving c=1. The offset is 844424930131968 and the extraction grid has spacing 0.125. Both inputs are ties; RNE extracts [1,−1]. The residual is [0.0625,0.0625], and the stored slice is [0.5,−0.5]. This is a complete worked iteration, so you can inspect each intermediate before coding a loop.

The assignment asks for one extraction, not the entire method. Make it return a structured trace with c, sigma, v, q and next. A failure can then be located in exponent selection, the two rounded operations, residual subtraction or encoding. Test negative entries too: the offset stays positive in this construction. Do not replace it with a sign-dependent trick without a separate derivation.

CHECKPOINT 08 / 14 · 150 MINUTES

Build a complete expansion and prove its inner sums

Build complete slices and test exactness using common-grid bounds.

Paper connection: §3 Eqs.9–11

One slice is not enough for a general binary64 value. Feed the residual back into the same extraction process until every residual entry is exactly zero. Save each E4M3 vector with its external exponent. After any number of iterations, the original vector should equal all saved scaled slices plus the current residual. This invariant is more informative than merely checking that the final answer looks close.

For our vector, the second residual is [1/16,1/16]. Its maximum gives c=−4. It is extracted completely and stored as [1,1]. Therefore x=2^1[0.5,−0.5]+2^−4[1,1]. The second component carries information the first could not store. This is how a collection of short values represents a much more precise object.

Why can FP32 sum slice products exactly? In the rho=49 regime, each normalized component is an integer multiple of 1/16 with magnitude at most one. Write it as a/16, |a|≤16. Products have integer numerators a×b over 256. At length k, the absolute numerator of every partial sum is bounded by 256k. For k≤65536 that bound is 2^24, inside the exact-integer range of binary32. The shared grid, bounded magnitude and reduction length together prove exactness. Arbitrary FP8 arrays do not inherit this proof.

Your program should distinguish a verified complete expansion from truncation. A maximum-iteration guard prevents a bug from looping forever, but hitting it is an error, not a successful approximate decomposition. Our small-domain course allows a generous cap such as 256 slices and reports unsupported_domain if it is reached. Inputs with widely separated exponents can demand far more slices than a simple precision/4 estimate suggests.

The familiar minimum pair-count table is a best-case cost guide. With the 0.75 extraction and well-scaled data, the residual can drop an additional bit through nearest rounding. Do not conclude that E4M3 needs exactly ceil(53/4) slices. Observe actual exponents and residuals before proposing a count formula.

CHECKPOINT 09 / 14 · 120 MINUTES

Reconstruct a dot product from all slice pairs

Assemble a dot product with explicit scale and accumulation order.

Paper connection: §3 Eq.10 and §4 accumulation-order discussion

Suppose x=X1+X2 and y=Y1+Y2. Distribution gives four terms: X1Y1, X1Y2, X2Y1 and X2Y2. Keeping only matching indices loses the cross terms. With sX and sY slices you need sX×sY dot products unless a separately justified algorithm intentionally approximates the result.

Each stored slice is normalized, so its external power of two must return during reconstruction. If x uses exponent cX and y uses cY, the dot of their normalized components is multiplied by 2^(cX+cY). These are not arbitrary scale factors learned from data: they encode exactly where the component belongs in the original number.

Our x expansion has two slices and y=[1,1] has one. The pair dots are [0.5,−0.5]·[1,1]=0 and [1,1]·[1,1]=2. Restore their scales: 2^1×0 plus 2^−4×2 = 0.125. This shows the full method on one output without hiding any intermediate. The low slice matters because the large terms cancel.

The real-arithmetic expansion is exact, but a finite sequence of binary64 additions can round. We choose increasing absolute value of scaled partials, with stable slice-index tie breaks, as the course's reproducible order. This is a teaching convention; the exact optimized order in the author implementation remains to be verified. It does not guarantee correct rounding of every final dot product.

Test two different questions separately. First, do the exact scaled partials sum to the exact input dot? This checks decomposition and pair coverage. Second, does the chosen rounded accumulation satisfy its computed error bound? This checks the final numerical step. An answer can pass both without matching another library's different reduction order bit for bit.

Lift the dot product into matrix multiplication

Implement small rectangular GEMM and validate row/column scale indexing.

Paper connection: §3 matrix extension; §4 memory layout

For A with shape m×k and B with shape k×n, C has shape m×n. Entry C[i,j] is the dot of row i of A with column j of B. The repeated inner dimension k is the length that controls the slice budget. Neither m nor n can replace it in that formula.

For A=[[1,2],[3,4]] and B=[[5,6],[7,8]], C is [[19,22],[43,50]]. Work out C[0,1]=1×6+2×8=22 before thinking about optimization. Your first matrix implementation should call the tested dot method for each entry. This is deliberately transparent and slow. It verifies indexing before introducing slice-plane GEMMs.

To use a fast GEMM backend, collect slice number p from every A row into a matrix Q_A[p], and slice number q from every B column into Q_B[q]. Their ordinary matrix product computes all normalized pair dots at once. Rows and columns can need different numbers of slices; missing slices are zero-padded. The external scale remains specific to output row and column: cA[i,p]+cB[j,q]. One global scale per whole matrix silently changes the construction.

A transpose in a GPU implementation often supports memory access, not a different mathematical product. The paper discusses transposing A and using a TN kernel. Keep logical shapes separate from the physical storage layout. A visual of row/column intersections is more useful here than memorizing a library flag.

CHECKPOINT 11 / 14 · 120 MINUTES

Measure error without fooling yourself

Produce reliable error reports and distinguish algorithm error from conditioning.

Paper connection: §5.3 and Fig.3; numerical-analysis prerequisite

An absolute error is |computed−reference|. A relative error divides that by |reference|, which is undefined when the reference is zero. A ULP error measures discrepancy on the floating-point grid, and needs an explicitly chosen convention. A small mean error can hide a catastrophic worst case; record maxima and representative traces as well.

For this course, use exact rational arithmetic for small binary64-input dot products and matrices. Every finite binary64 value is an exact rational with a power-of-two denominator, so this oracle need not approximate the input. For larger experiments, use MPFR at 128 and then 256 bits, increasing precision when the rounded reference changes. Simply choosing 128 bits does not make every adversarial cancellation experiment exact.

If the target is zero, display relative error as undefined and retain the absolute error. Do not replace the denominator by an arbitrary 1e−12: that can make a bad result look acceptable. For normal nonzero references, report both the absolute discrepancy and a clearly named spacing-normalized error, |computed−reference|/ulp(reference). At binade boundaries, adjacent spacing differs by direction, so do not confuse this with an integer count of representable values between two encodings.

Conditioning explains why a tiny relative input perturbation may cause a large relative output perturbation. For a nonzero dot result s, a useful indicator is kappa=Σ|x_i y_i|/|s|. If terms nearly cancel, the numerator is large while the denominator is small. That describes sensitivity of the problem, independently of whether our implementation is correct.

For reconstruction with exact partials t_l, the sequential-sum bound is g_(L−1)Σ|t_l|, where g_j=ju/(1−ju) and u=2^−53. It is an absolute bound and assumes no overflow or underflow. Do not replace it by a universal “within 1e−5.” Conversely, a deliberately conservative bound is not evidence that typical accuracy is poor. Show the measured error and the bound separately.

Remove native FP64 arithmetic with integer significands

Implement restricted-domain binary64 multiplication without float arithmetic in its core.

Paper connection: §4.2 and Listing1

“Without FP64 arithmetic” can sound like every computation uses FP8. That is not the architecture. Splitting and reconstruction still need binary64 semantics. One way to provide them on a processor with weak FP64 support is to implement the necessary operations using integers. The representation remains a 64-bit floating-point encoding even when the execution units are integer units.

For normal binary64 values, write x=(−1)^s M×2^(e−52), with a 53-bit integer M. To multiply two values, multiply their integer significands exactly, combine signs with XOR, and add exponents with the appropriate scaling. A 53×53 product needs up to 106 bits. Normalize that product to a 53-bit retained significand and apply the RNE primitive. If rounding overflows the significand, adjust the exponent again.

A small analogy uses three-bit significands: 1.5×1.75 corresponds to (6/4)×(7/4)=42/16=2.625. The exact product is 10.101₂. Keeping three significant bits requires a rounding decision; it is not enough to multiply and throw away the low bits. The actual binary64 multiplication uses the same structure with more bits.

Python's arbitrary-width integers make this first implementation easy to inspect. They do not prove that a CUDA implementation using 32/64-bit limbs is fast or correct. Listing1 illustrates limb multiplication in the paper; carry propagation, exponent handling, normalization and rounding remain essential around it. Addition is a separate, substantial problem because exponent alignment must preserve guard and sticky information, especially under cancellation.

The required assignment implements multiplication for finite normal inputs whose result is normal, plus explicitly handled zeros. Reject overflow, subnormal outputs, infinities and NaNs. A provided and separately validated restricted-domain integer adder will later support the capstone. Building a fully compliant IEEE754 library is a different project. The course's emulator contract is deliberately honest about its limits.

Blocking trades matrix work against reconstruction work

Implement inner-dimension blocking and explain its accuracy/cost tradeoff.

Paper connection: §4.3; §5.2 versus §5.4; Fig.5

Partition the inner dimension k into blocks. A dot product becomes a sum of shorter dot products; a matrix product becomes a sum of matrix products over matching k panels. Shorter reductions can allow wider slices and fewer pair products, but each block creates another result that must be accumulated. This is a tradeoff, not a monotonic rule that smaller blocks are faster.

For a length-four dot, splitting after two elements yields x0y0+x1y1 and x2y2+x3y3. Each block can be computed correctly, yet adding the two rounded block results introduces a new rounding opportunity. With cancellation across blocks, differences from an unblocked schedule can become visible even when each block was internally exact before reconstruction.

The paper's discussion contains two different optimization objectives. A k block of 1024 looks attractive when balancing FP16 GEMM count and kernel throughput. The overall timings later favor 4096 among the tested block sizes because accumulation and memory costs also matter. A good experiment does not confuse a fast subroutine with a fast complete application.

The simplest cost model is T_total=T_split+T_pair_products+T_reconstruct+T_other. Pair-product work roughly scales with the number of pairs times the GEMM dimensions, but throughput also depends on shape. Slice workspace can shrink when only a block is resident. Conversely, repeatedly updating the full C matrix increases traffic. Neither FP8 peak throughput nor GEMM count alone predicts the total.

Implement blocked and unblocked semantic paths using the same validated primitives. Record the number of blocks, actual slice counts, number of pair products and result error. CPU wall-clock measurements are useful for debugging your implementation but must not be presented as reproduced GPU speedups. For an optional GPU study, include warmup, synchronization and timing distributions, with allocation and transfer policy explicitly recorded.
